What a SCADA FAT Review Should Catch

By Ahmed Osama Mohamed · November 2026

A Factory Acceptance Test (FAT) is the last controlled chance to find problems in a SCADA system before it reaches site, where every fix costs more time and carries more operational risk. A FAT review is an independent check that the test is designed to find those problems, and that the evidence proves they are absent.

1. Does the test procedure trace to the specification?

Every requirement in the Functional Design Specification (FDS) and Detailed Design Specification (DDS) should map to at least one test step. Look for requirements with no test, tests that reference no requirement, and vague pass criteria such as “system operates correctly”. A traceability matrix is the quickest way to expose gaps.

2. Is the test environment representative?

Check which parts of the system are real and which are simulated. Simulated field I/O is normal at FAT, but the review should confirm that the simulation covers abnormal conditions (bad quality, comms loss, out-of-range values), not only the happy path. Software versions and configuration under test must match what will be shipped.

3. Are failure and recovery cases covered?

  • Server, network and communication-link failover, and the time to recover.
  • Loss and restoration of RTU or PLC communications, including data catch-up.
  • Alarm behaviour under load, such as alarm floods, acknowledgement, shelving and priority handling.
  • Historian gaps and back-filling after an outage.

4. Are performance requirements actually measured?

Display call-up times, update rates, polling cycles and tag capacity should be measured against the specified numbers, with the load stated. “Looked fast” is not evidence.

5. Is cybersecurity part of the test?

Confirm that user roles, access rights, logging and network segmentation are tested as designed, and that default credentials and unused services are removed. OT security is far cheaper to fix on the factory floor than after commissioning.

6. Is the evidence good enough?

Each result should be recorded with who ran it, when, on which software version, and with the actual observed values. Failed tests need a tracked punch item with an owner and a retest, not a note saying “to be fixed”. Open items should be classified by their effect on safety and operation, so that it is clear what blocks shipment.

7. Will it carry through to IFAT and SAT?

A good FAT hands over cleanly. Test cases that cannot be repeated on site, or interfaces that were never tested with the real counterpart system, are exactly the items that surface later at the Integrated FAT (IFAT) or Site Acceptance Test (SAT). A reviewer should flag them early.
